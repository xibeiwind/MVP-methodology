# 软件开发中的 MVP 方法论 · 完全手册

> 一套可以直接拿去用的 MVP 知识体系：概念本质 → 假设与实验 → 流程与指标 → 工程与组织落地 → 反模式与案例 → 模板与 90 天路线图。

---

## 一句话抓住 MVP

**MVP 不是"功能最少的版本"，而是"针对最大风险假设、成本最低、证据可信的一次实验"。**

把它写成一个可执行的等式：

```
MVP = 一个高风险假设 + 最小可执行的实验载体 + 可观测的指标 + 事先写好的决策规则
```

四要素缺任何一个，你做的就不是 MVP，而是"缩小版的产品"或"给老板看的演示"。

---

## 为什么要学它（解决的是哪类问题）

软件项目最贵的成本不是写代码，而是**在错误的方向上正确地写了很多代码**。行业里反复出现的失败模式极其稳定：

- 需求是拍脑袋的，做完了才发现用户不买；
- 用户说"这个功能挺好"，上线后没人用；
- 团队花了 9 个月做出 1.0，市场窗口已经关了；
- 为了"快"，砍掉了质量和可观测性，结果拿不到数据，等于白做；
- 老板要看到"完整的东西"，MVP 被做成了缩小版正式版。

MVP 方法论就是针对这些失败模式的一套**降低不确定性、把决策建立在证据上**的工程与管理实践。

## 30 分钟速览：20 条要点

1. **MVP 的产出是"知识"，不是"软件"。** 软件只是获取知识的载体。
2. **先决定要学什么，再决定要做什么。** 实践中的顺序是 Learn → Build → Measure，不是反过来。
3. **只测最大的那个风险。** 用 RAT（Riskiest Assumption Test）思维排优先级：影响大 × 不确定性高的先测。
4. **假设要能被证伪。** 写不出"什么结果会让我们放弃"的假设，不是假设，是愿望。
5. **证据有硬度差别。** 用户说"会买" < 留下邮箱 < 预约通话 < 真的用 < 真的付钱 < 复购 < 主动推荐。假设风险越高，越需要硬证据。
6. **能不做产品就不要做产品。** 落地页、视频、人工服务（concierge）、人工后台（Wizard of Oz）常常比写代码更快更准。
7. **"最小"约束的是范围，不是质量。** 用户能碰到的那一条路径必须是完整、可靠、可信任的；被砍掉的是"不在验证范围内的功能"。
8. **MVP 必须是端到端可用的垂直切片**（walking skeleton）：真实用户、真实流程、真实数据，哪怕只覆盖一个场景。
9. **没有埋点就没有 MVP。** 上线前先定义好事件、指标、观测窗口，否则你只是发布了一个产品，没有做实验。
10. **指标要可执行、可访问、可审计。** 注册总数、累计下载量是虚荣指标；激活率、留存曲线、付费转化才是。
11. **事先写下决策规则。** "如果 4 周内 X ≥ 15%，就继续；8%–15% 迭代；< 8% 转向或停止。" 没有规则的实验一定会被事后合理化。
12. **技术债可以欠，但要登记。** 区分"有意/审慎"和"无意/鲁莽"，MVP 结束后必须安排偿还窗口。
13. **优先可逆决策。** 数据库、账号体系、数据模型属于单向门，要多想；UI、文案、排序属于双向门，快速试。
14. **MVP 是循环，不是阶段。** 一个 MVP 验证完，下一个 MVP 面向新的最大风险。
15. **时间盒比范围更重要。** 固定时间、固定人，砍范围。典型验证周期 4–8 周。
16. **团队必须有决策权。** 没有权力做 pivot 的团队，学习循环是断的，MVP 会退化成"交付里程碑"。
17. **不要用内部共识替代用户证据。** 老板、销售、投资人的意见都是假设，不是数据。
18. **合成数据和 AI 角色扮演只能做预筛，不能做验证。** 它们能帮你省钱，但不能替你承担后果。
19. **最常见的失败：MVP 变成"最小可憎产品"（Minimum Viable Junk）**——既不可用也不可信，还没验证任何假设。
20. **判断成功的标准只有一条：** 这个 MVP 是否让我们在花掉下一笔大钱之前，明确地知道该继续、该改、还是该停。

## 使用建议

- 第一次读：按 01 → 02 → 03 顺序，先把"假设—实验—指标—决策"这条主线吃透。
- 真正做项目时：把 [06-模板与路线图.md](06-模板与路线图.md) 里的**假设卡**和**实验设计卡**打印出来，填不满就说明还没想清楚。
